# RFC-015 — Audit Storage and Immutability

## Status

**PROPOSED — Architecture Review Required**

## Context

PS-008 requires a PostgreSQL-compatible, append-only source of truth that remains queryable by tenant, time, actor, resource and correlation. Application conventions alone cannot guarantee immutability when migrations, administrative sessions or compromised credentials can issue direct writes.

This RFC defines the decision surface Architecture must approve. It does not authorize implementation or production retention periods.

## Decision drivers

- No ordinary update or individual deletion path.
- Atomic participation in the shared transaction model.
- Strong Organization isolation and restricted security-event access.
- Stable query pagination at growing volume.
- Additive schema evolution and interpretable historical contracts.
- Operationally feasible PostgreSQL backup, restore and future partitioning.

## Proposed decision

Use one canonical PostgreSQL `audit_event` relation behind a dedicated persistence adapter. The relation is append-only for application roles. Audit writes use a narrowly scoped insert-only database role; readers and exporters use separate read roles with different grants.

The initial logical schema contains:

- Immutable identifiers, event and schema versions.
- `occurred_at` and database-generated `recorded_at`.
- Actor, Organization, optional Partner/Workspace scope.
- Resource, action and result.
- Correlation, causation and request references.
- Sanitized `jsonb` metadata and changes.
- Retention category and data classification references.

No application repository exposes `update`, `delete` or arbitrary SQL mutation methods for AuditEvent.

## Immutability controls

Architecture must approve defense in depth:

1. Revoke `UPDATE`, `DELETE` and `TRUNCATE` from runtime roles.
2. Grant the writer only the minimum insert and sequence privileges.
3. Add a database trigger that rejects `UPDATE` and `DELETE` unless an approved maintenance role and explicit audited procedure are active.
4. Keep ownership and migration credentials outside application runtime.
5. Audit use of maintenance procedures in a separate protected administrative evidence path.
6. Prevent mutable foreign-key cascades from deleting evidence; identifiers are historical values, not ownership references requiring cascade.

Controlled privacy transformations are not ordinary updates. They require the procedure defined by RFC-017, preserve structural fields and record policy version, reason, actor and affected range. Architecture must decide whether the transformed representation is stored as a superseding privacy overlay or a privileged field-minimization procedure; direct row editing remains prohibited.

## Keys and consistency

- `id` is globally unique and non-reusable.
- `recorded_at` is generated by PostgreSQL and never supplied by untrusted callers.
- Stable ordering is `(occurred_at, recorded_at, id)`; timestamps alone are not uniqueness guarantees.
- One confirmed event is unique on the normalized idempotency tuple defined by RFC-016.
- `result` is constrained to `success`, `denied` or `failed`.
- `metadata`, `changes`, actor and scope fields are validated before insert and constrained to defined maximum sizes.

## Indexing and query model

Initial indexes should support:

- `(organization_id, occurred_at, id)`
- `(organization_id, partner_id, occurred_at, id)`
- `(organization_id, workspace_id, occurred_at, id)`
- `(organization_id, actor_id, occurred_at, id)`
- `(organization_id, resource_type, resource_id, occurred_at, id)`
- `(organization_id, correlation_id)`
- retention category and recorded time for policy execution

Search uses keyset pagination, mandatory time bounds for broad queries and explicit maximum page/export sizes. JSON fields are not generically indexed in v1; promoted search fields require additive schema changes justified by observed queries.

## Partitioning and lifecycle

The v1 contract must not require partitioning. The physical design keeps a future time-based partition key compatible with queries and retention. Before partitioning, Architecture must validate uniqueness semantics, cross-partition indexes, backup/restore, legal hold behavior and the effect of detaching or dropping partitions.

Retention never relies on ad hoc `DELETE`. It runs only through the versioned policy mechanism in RFC-017. Dropping a partition is allowed only if the same authorization, hold checks and evidence requirements are met.

## Migrations and compatibility

- Migrations are additive by default.
- Existing `schemaVersion` values remain readable.
- Renames use expand/migrate/contract and do not reinterpret historical payloads.
- Backfills use maintenance credentials, bounded batches and an auditable plan.
- Restore exercises verify Audit records, constraints, grants and triggers, not only row count.

## Alternatives considered

### Application-enforced append-only

Rejected as the sole control because it does not protect against direct SQL, privilege mistakes or future repository methods.

### External WORM or ledger storage

Deferred. It adds operational complexity not required by PS-008 v1 and does not remove the need for scoped PostgreSQL queries.

### Event Bus as canonical store

Rejected. Delivery infrastructure does not provide the authorized query, retention and privacy model required by Audit™.

### Cryptographic hash chain

Deferred. It can improve tamper evidence but requires key custody, verification and repair procedures. Database permissions, triggers and operational controls are required first.

## Failure and recovery

- An insert failure is returned to the transaction coordinator and never reported as success.
- A restore that omits grants, constraints or triggers is incomplete.
- Replica lag cannot be used for read-after-write verification of critical evidence.
- Administrative bypass failure must fail closed and must not silently enable ordinary mutation.

## Verification required before approval

- Migration test proves runtime roles cannot update, delete or truncate.
- Repository surface exposes insert/read only.
- Duplicate confirmed events are rejected consistently.
- Tenant and security classification filters are mandatory in query adapters.
- Keyset pagination remains stable with equal timestamps.
- Backup/restore exercise preserves rows, constraints, grants and triggers.

## Consequences

The proposal supports PS-008 without modifying Foundation or PS-004–PS-007. It introduces new database roles, migrations and operational procedures when Engineering begins. Those implementation changes are explicitly outside this documentation branch.

## Architecture questions

1. Approve trigger plus privilege enforcement, or require a stronger maintenance boundary?
2. Choose privacy overlay versus privileged minimization procedure with equivalent traceability.
3. Confirm identifier type and maximum JSON payload sizes under existing platform conventions.
4. Define the volume threshold and approval gate for partitioning.
